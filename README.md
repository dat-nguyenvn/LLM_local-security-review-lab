# Security Agent Playground

A small security training lab for practicing source-code reviews. It contains
two intentionally vulnerable apps, a rule-based scanner, and an LLM agent that
uses a local Ollama model.

> **Warning:** This repository intentionally contains insecure training code.
> Run it only on your own computer. Do not deploy it publicly, use it with real
> data, or reuse its vulnerable patterns in production. The Python app and the
> web server examples below bind to `127.0.0.1`.

## Repository structure

```text
.
├── app1/                   # HTML/CSS/JavaScript web app
├── app2/                   # Python HTTP app
├── security_agent.py       # Rule-based source scanner
├── llm_security_agent.py   # Source review using local Ollama
└── README.md
```

## Requirements

- Conda.
- Ollama and the `qwen2.5-coder:3b` model to use the LLM agent.
- No third-party Python packages are required.

## Installation

### 1. Get the source code

If you have already cloned the repository:

```bash
cd LLM_local-security-review-lab
```

Or clone it from GitHub:

```bash
git clone https://github.com/dat-nguyenvn/LLM_local-security-review-lab.git
cd LLM_local-security-review-lab
```

### 2. Create and activate the Conda environment

```bash
conda create -n sam3 python=3.12
conda activate sam3
```

### 3. Install and prepare Ollama

Install Ollama by following the instructions for your operating system at
[ollama.com/download](https://ollama.com/download).

Download the model once:

```bash
ollama pull qwen2.5-coder:3b
```

Ollama manages the model in its local model store. The exact location depends
on your operating system and the account running Ollama.

## Run the applications

Run each command below in a separate terminal from the repository root.

### App 1: Web app

```bash
python3 -m http.server 8001 --bind 127.0.0.1 --directory app1
```

Open <http://127.0.0.1:8001> in your browser. Stop the server with `Ctrl+C`.

### App 2: Python app

```bash
python3 app2/app.py
```

Open <http://127.0.0.1:8002> in your browser. Stop the server with `Ctrl+C`.

## Run the security agents

### Rule-based scanner

```bash
python3 security_agent.py
```

The scanner looks for a small set of known source-code patterns. It does not
use an LLM, run the apps, or scan the network.

### Local LLM agent

Make sure Ollama is running. If it does not start automatically, open a separate
terminal and run:

```bash
ollama serve
```

Then, from the repository root, run:

```bash
python3 llm_security_agent.py
```

The agent sends the source code of `app1/index.html`, `app1/app.js`, and
`app2/app.py` to Ollama on `localhost`. It only reads source code; it does not
run the apps or scan the network. To select a different model already installed
in Ollama:

```bash
python3 llm_security_agent.py --model <model-name>
```

The agent only allows an Ollama server on localhost to help prevent source code
from being sent to an external service. LLM reports can miss issues or include
false positives, so verify all findings manually.

## Example scan results

The following examples were captured from the commands above. Rule-based results
are repeatable for the current source, while LLM results can vary between runs
and model versions.

### Rule-based scanner

```text
Python Security Agent - local source scan (does not run apps or scan networks)
Scope: app1/app.js and app2/app.py

[app1/app.js]
  MEDIUM - line 4: A hard-coded credential in JavaScript is visible to every user.
    Recommendation: Keep secrets out of frontend code; store them on the backend and rotate any exposed real credential.
  HIGH - line 9: User input is inserted into innerHTML, which can cause DOM-based XSS.
    Recommendation: Use textContent for plain text, or sanitize HTML with a trusted library.

[app2/app.py]
  HIGH - line 58: SQL is concatenated with input instead of using parameter binding.
    Recommendation: Use a parameterized query, for example WHERE name LIKE ?, and pass the value separately.
  HIGH - line 71: A user-supplied filename is joined to a path without restricting it to the intended directory.
    Recommendation: Resolve the path and reject it unless it remains inside PUBLIC_DIR.

Summary: 4 rule-based finding(s).
This is a rule-based static analyzer, not an LLM; manually review its results.
```

### Local LLM agent

This is an illustrative, unverified model response. Its severity ratings and
confidence scores are generated by the model and are not calibrated.

```text
LLM SECURITY REVIEW
Several security vulnerabilities found in the provided source code.

1. [CRITICAL] Insecure HTML injection in JavaScript (confidence 10/10)
   File: app1/index.html:7-8
   Evidence: <script src="app.js" defer></script>
   Impact: An attacker could inject malicious JavaScript into the page by manipulating the HTML structure, potentially leading to XSS (Cross-Site Scripting) attacks.
   Recommendation: Use a content security policy (CSP) to restrict the sources of scripts that can be executed, or use a templating engine that supports automatic escaping.

2. [CRITICAL] Insecure input handling and secret exposure (confidence 10/10)
   File: app1/app.js:10-11
   Evidence: const DEMO_PASSWORD = "admin123";
   Impact: An attacker could exploit this hardcoded password to gain unauthorized access to the application.
   Recommendation: Use environment variables or a secure configuration management system to store sensitive information like passwords.

3. [CRITICAL] Insecure SQL query construction (confidence 10/10)
   File: app2/app.py:24-26
   Evidence: sql = "SELECT name FROM items WHERE name LIKE '%" + term + "%'"
   Impact: An attacker could inject malicious SQL into the query, potentially leading to SQL injection attacks.
   Recommendation: Use parameterized queries or a database library that supports them to prevent SQL injection.

4. [CRITICAL] Insecure file path handling (confidence 10/10)
   File: app2/app.py:30-33
   Evidence: file_path = PUBLIC_DIR / filename
   Impact: An attacker could manipulate the file path to access files outside of the public directory, potentially leading to unauthorized access.
   Recommendation: Validate and sanitize file paths to prevent directory traversal attacks.

An LLM can miss issues or produce false positives; verify findings manually.
```

**Review note:** The LLM example above contains inaccurate evidence and line
references. Including a script tag in `app1/index.html` does not, by itself,
establish an injection vulnerability, and the hard-coded demo credential is at
`app1/app.js:4`, not lines 10-11. The SQL injection and path traversal patterns
are present in `app2/app.py` around lines 58 and 71, not the cited ranges.
Their impact is limited by this localhost-only training setup. Treat model
output as triage assistance, confirm every finding against the cited source,
and do not rely on model severity or confidence ratings as a substitute for
analyst judgment.

## Intentional training vulnerabilities

- **App 1:** inserts user input into `innerHTML`; checks a demo access code and
  displays the protected content in browser-side JavaScript.
- **App 2:** concatenates a search term into SQL; joins a user-supplied filename
  to a path without restricting it to the `public/` directory.

Use these examples only to learn how to identify and fix vulnerabilities. Do
not test against systems or data you do not own or have permission to assess.
